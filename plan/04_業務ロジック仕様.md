## 1. 記録の状態

| 状態 | 削除フラグ | 説明 |
|---|---|---|
| 有効 | FALSE | 普通の記録 |
| 削除済み | TRUE | 論理削除。管理者が「削除済みも表示」にしたときだけ見える |

承認の流れはない。

## 2. 権限

### 2.1 役割の判定
1. `ctx.operatorId` が入力者マスタの**有効な人**でなければ、`AUTH_REQUIRED`（操作者を選び直してもらう）。
2. `ctx.token` が有効（§3.3）なら「管理者」、そうでなければ「設定者」。
3. 本人かどうか（K-04）: `record.setterId === ctx.operatorId` かつ `record.source === 'アプリ'` かつ `record.deleted === false`。

### 2.2 権限の表

| 操作 | action | 設定者（本人） | 設定者（他人） | 管理者 |
|---|---|---|---|---|
| 登録 | CREATE | ○ | ― | ○ |
| 閲覧（有効な記録） | ― | ○ | ○ | ○ |
| 閲覧（削除済み） | ― | × | × | ○ |
| 修正（アプリの記録） | UPDATE | ○（期限なし。D-09） | × | ○ |
| 修正（移行データ） | UPDATE | × | × | ○（D-11） |
| 設定者を変える修正 | UPDATE | × | × | ○ |
| 削除 | DELETE | × | × | ○ |
| 元に戻す | RESTORE | × | × | ○ |
| 操作ログの閲覧 | ― | × | × | ○ |

- 管理者の権限が要る操作で、トークンがない・切れているときは `AUTH_REQUIRED` を返す。画面は管理者認証のダイアログを出し、認証できたらやり直す。
- 権限がないときは `FORBIDDEN` を返す。
- 画面のボタンの出し分けは、`getRecord` が返す `canEdit` / `canDelete` / `canRestore` / `canChangeSetter` に従う。

## 3. 管理者の認証

### 3.1 パスワードの置き場所（2026/11/15 フェーズ9 で変更: スクリプトプロパティ `ADMIN_PASSWORD`。正は docs/04 第1部 §3.1、plan/11）
- スクリプトプロパティ `ADMIN_PASSWORD` に、持ち主が GAS エディタで入れる。2文字以上、文字の種類は自由。無いときは誰も入れない。
- 変えても、発行済みのトークンはそのまま期限まで有効（キャッシュを消す処理はしない）。

### 3.2 照合（`authenticateAdmin`）
1. ロック中（キャッシュ `pinlock` がある）なら `AUTH_LOCKED`（残りの分数を message に入れる）。
2. ハッシュが一致すれば、失敗回数（キャッシュ `pinfail`）を消し、トークンを発行する。
3. 一致しなければ、失敗回数を＋1する（キャッシュの有効時間は PIN_LOCK_MINUTES）。PIN_MAX_FAILS に達したら `pinlock` を PIN_LOCK_MINUTES の間置き、`AUTH_LOCKED` を返す。それ以外は `AUTH_FAILED` を返す。
4. 成功も失敗もログに残す（§12）。失敗回数は「端末ごと」ではなく、アプリ全体で数える（K-20）。

### 3.3 トークン
- 発行: `token = Utilities.getUuid()`。`CacheService.getScriptCache().put('auth:' + token, JSON.stringify({operatorId, expiresAt}), AUTH_TOKEN_MINUTES * 60)`。
- 確認（`verifyAdmin_(ctx)`）: 次の3つがそろったときだけ有効。
  - キャッシュに `auth:` + token がある
  - 保存した operatorId が `ctx.operatorId` と同じ（操作者を変えたら、管理者モードは解ける）
  - 期限内
- 期限は延長しない（30分たったら入れ直す）。
- `logoutAdmin` でキャッシュから消す。

## 4. 入力チェック

サーバー側（【Validator】）で必ず行う。エラーは `VALIDATION` で返し、`fields` に項目ごとの文言を入れる。

| 項目 | キー | 規則 | エラーの文言 |
|---|---|---|---|
| 日付 | date | 必須。`yyyy/MM/dd` または `yyyy-MM-dd` で、実在する日付 | 日付を正しく入れてください |
| 時刻 | time | 必須。`H:mm` か `HH:mm`、0:00〜23:59。保存時に "HH:mm" にそろえる | 時刻を正しく入れてください |
| 設定パターン | pattern | 必須。基準パターンマスタにある番号。新規登録では有効なものだけ | パターンを選んでください |
| メインボイラ | fuel | 必須。`ガス` か `重油` | メインボイラを選んでください |
| 設定圧力 | pressure | 必須。数値で、小数2桁まで。PRESSURE_MIN 以上 PRESSURE_MAX 以下（K-07） | 0.50〜0.80 の範囲で、小数2桁までで入れてください |
| 設定者 | setterId | 必須（新規）。入力者マスタの有効な人。本人の操作では ctx.operatorId と同じでなければならない | 設定者を選んでください |
| 生産品種 | product | 任意。入れるときは品種マスタにある名前（修正のときは無効な品種もよい） | 品種を選び直してください |
| 備考 | note | 任意。NOTE_MAX_LENGTH 文字まで。前後の空白は取る | 備考は200文字までにしてください |

- 未来の日時（今より FUTURE_WARN_MINUTES 分以上先）はエラーにしない。画面の確認ダイアログで注意する（K-08）。
- 修正では、もとの記録の値のうち、マスタで無効になったもの（パターン、品種、設定者）は、変えていなければそのまま認める。
- システムの項目（記録ID、登録日時、版数、データ区分 など）は payload から受け取らない。

## 5. 圧力の自動入力とマスタとの差異

- 画面: パターンを選んだら、そのパターンのメイン圧力を圧力の欄に入れる。手で変えたあとにパターンを選び直したときも、上書きする。
- 画面: 圧力がメイン圧力と違えば、欄の下に注意を出す（文言は 05 §8 の M-21）。
- サーバー: 保存のときに `masterDiff = (round2(pressure) !== round2(pattern.mainPressure))` を計算して保存する（K-09）。比較は小数2桁に丸めた整数（×100）で行い、浮動小数の誤差を避ける。
- 修正で圧力かパターンを変えたときだけ、計算し直す。

## 6. 保存の流れ

すべて `withLock_` の中で行う（§11）。

### 6.1 登録（`createRecord`）
1. 役割を判定する（§2.1）。
2. 入力チェック（§4）。
3. `changedAt` を日付と時刻から作る。
4. 採番する（§10）。
5. masterDiff を計算する（§5）。
6. `setterName` は入力者マスタの記入称、`source='アプリ'`、`version=1`、`deleted=false`、登録者と更新者は ctx.operatorId、登録日時と更新日時は今。
7. 末尾に1行足す。
8. ログ「登録」を書く。
9. `{recordId, version, masterDiff}` を返す。

### 6.2 修正（`updateRecord`）
1. 役割を判定する。
2. 記録を ID で探す。なければ `NOT_FOUND`。削除済みも `NOT_FOUND`。
3. `version` が違えば `CONFLICT`。
4. 権限を確かめる（§2.2）。本人のときに setterId が変わっていたら `FORBIDDEN`。
5. 入力チェック。
6. 変わった項目だけ反映する。changedAt、setterName、masterDiff は必要なら作り直す。
7. 更新者と更新日時を入れ、version を＋1する。
8. ログ「修正」を書く（detail に変わった項目のキーと、変更前・変更後の値を入れる）。
9. `{recordId, version, masterDiff}` を返す。
- 変更日時の日付が変わっても、記録ID は変えない。

### 6.3 削除（`deleteRecord`）と元に戻す（`restoreRecord`）
1. 管理者であることを確かめる。
2. 記録を探し、version を比べる。
3. 削除: `deleted=true`、削除日時と削除者を入れる。元に戻す: `deleted=false`、削除日時と削除者を空にする。どちらも更新者・更新日時を入れ、version を＋1する。
4. ログ「削除」／「削除の取り消し」を書く。

## 7. 今の設定と直近の記録

- 今の設定（K-10）: 削除されていない記録を、changedAt の新しい順、同じなら createdAt の新しい順に並べたときの先頭。記録が1件もなければ `null`。

## 8. 履歴の検索と並び順

- 条件（すべて任意。指定したものは AND で絞る）:

| 条件 | キー | 規則 |
|---|---|---|
| 期間（から） | dateFrom | date ≧ dateFrom |
| 期間（まで） | dateTo | date ≦ dateTo |
| パターン | pattern | 一致 |
| メインボイラ | fuel | 一致 |
| 設定者 | setterId | 一致（無効な人も選べる） |
| 生産品種 | product | 一致。`（未設定）` を選んだら空のもの |
| 削除済みも表示 | includeDeleted | 管理者のときだけ有効。設定者が true にしても無視する |

- 並び順: §7 と同じ（新しい順）。
- ページ分け: `offset` から PAGE_SIZE 件。返す値は `{items, total, hasMore}`（K-11）。

## 9. 日時の扱い

- タイムゾーンは Asia/Tokyo に固定する（appsscript.json と `Utilities.formatDate` の両方）。
- 時刻はテキスト "HH:mm" で保存する（K-01）。シートに書くときは、その列の書式を `@` にしてから書く。
- changedAt は `new Date(年, 月-1, 日, 時, 分)` で作り、DT としてシートに書く。
- 画面には `yyyy/MM/dd HH:mm` の文字列で返す。日付だけは `yyyy/MM/dd`。
- 画面の `input type="date"` は `yyyy-MM-dd` を送るので、サーバーで `yyyy/MM/dd` にそろえる。

---

## 10. 記録ID の採番

- 形式: `{RECORD_ID_PREFIX}-{yyyyMMdd}-{連番}`（K-05）。例: `BP-20261114-001`。
- 日付は changedAt の日付。
- 連番: ロックの中で、同じ `BP-yyyyMMdd-` で始まる ID の連番の最大値に＋1する。削除済みも数える。3桁ゼロ埋めにし、1000件目からはそのまま4桁にする。
- 移行データも同じ規則で、changedAt の古い順に振る（§13.4）。

---

## 11. 排他制御と楽観ロック

- 書き込みのある公開関数は、すべて `withLock_(fn)` で包む。中で `LockService.getScriptLock().tryLock(10000)` を呼ぶ。
  - 取れなければ `BUSY`（M-41）。
  - 入れ子で呼ばれたときは、ロックを取り直さない（ロックの深さを持つ変数で判定する）。
- 修正・削除・元に戻すでは、ロックの中で行を読み直し、`version` を比べる。違えば `CONFLICT`（M-42）。
- 行は記録ID で探す（`findRowIndex_`）。物理削除はしないので、行の位置は変わらない。

## 13. 既存データの移行

### 13.1 全体の流れ
1. 変換（Node）: `node tools/migrate/convert_excel.js "reference/ボイラ圧力設定変更履歴.xlsx" "reference/移行データ"`
2. ユーザーが `report.md` を確認する（特に品種の振り分けと、該当しなかった備考）。
3. ユーザーが4つの CSV を移行用フォルダに置き、設定シートに MIGRATION_FOLDER_ID を入れる。
4. ユーザーがメニュー「移行データ取込」（`menuImportMigration`）を実行する。
5. 取込の結果（件数と内訳）をダイアログに表示し、照合する（§13.5）。

### 13.2 変換スクリプト（`convert_excel.js`）の規則
- 外部ライブラリは使わない。`child_process.execFileSync('unzip', ['-p', xlsx, 'xl/...'])` で XML を読み、正規表現で解析する（K-15）。
- シートの場所: `xl/workbook.xml` のシート名と `xl/_rels/workbook.xml.rels` の対応から、シートの XML を決める。
- 共有文字列（`xl/sharedStrings.xml`）: `<si>` ごとに、`<t>` と `<r><t>` の文字をつなげる。**`<rPh>`（読み仮名）の中は読まない**（D-28）。XML の実体参照（`&amp;` など）を戻す。
- セル: `t="s"` は共有文字列、`t="str"` / `t="inlineStr"` は文字列、それ以外は数値として読む。
- 日付（A列）: シリアル値を `1899-12-30` からの日数として `yyyy/MM/dd` にする。
- 時刻（B列）: 文字列なら全角を半角にして（NFKC）、`^(\d{1,2}):(\d{2})$` に当てはめて "HH:mm" にする。数値なら `Math.round(値 × 1440)` 分を "HH:mm" にする（0 は "00:00"。D-22）。どちらでもなければエラーにし、レポートに出す。
- パターン（C列）: 整数。
- 燃料（D列）: `ガス` / `重油` 以外はエラー。
- 圧力（E列）: 小数2桁に丸める。
- 設定者（F列）と入力者マスタの記入称: 前後の空白を取る。全角の英数字は半角にする（入力者マスタの `ｙ` → `y`。2026/11/15 の依頼で、以前の「`y` を `ｙ` にそろえる」から変えた）。大文字・小文字は変えない（`Y` は別の人）。空はそのまま空。（docs/04 が正）
- 備考（G列）: 前後の空白を取る。文字はそのまま残す（全角の「２L」なども変えない）。
- 空の行（A列が空）は読み飛ばす。読んだ件数が154件でなければ、レポートの先頭に警告を出す（本番前に件数が増えているのは正常）。
- 入力者: 入力者マスタのシートから記入称と氏名を読み、並び順で U01〜を振る。氏名は全角スペースを含めてそのまま、ただし読み仮名は取り除く。履歴にあってマスタにない記入称（「ヒ」）は、続きの番号で `active=FALSE`、`note=退職` として足す。
- パターン: 基準パターンマスタのシートを読み、主要品種の欄から「メイン圧力: 0.66（小型）」のような形の括弧の中を取り出す。取り出せなければ空にする。

### 13.3 品種の振り分け規則（K-16）
備考を NFKC で正規化したあと、上から順に当てはめ、最初に当てはまったものにする。規則は `tools/migrate/product_rules.json` に持つ。

| 順 | 正規表現 | 品種 |
|---|---|---|
| 1 | `麦茶` | 2L麦茶 |
| 2 | `2L\s*\(?水` | 2L(水) |
| 3 | `2L` | 2L(その他) |
| 4 | `1\.5L` | 1.5L |
| 5 | `0\.525` | 0.525L(スポーツ) |
| 6 | `0\.55\|550\s*ml` | 0.55L(水) |
| 7 | `0\.5\s*(k\|m\|L)` | 0.5L |
| 8 | `0\.35` | 0.35L |
| 9 | `小型\|(^\|[^.\d])1L` | 小型 |
| 10 | `CUP` | CUP有 |

- 表の中の `\|` は、表の区切りと区別するための書き方で、JSON では `|`（または）と書く。
- どれにも当てはまらなければ空（「その他」にはしない）。
- レポートに「品種ごとの件数」と「当てはまらなかった備考の一覧（行番号つき）」を出す。

### 13.4 取込（`menuImportMigration`）
1. 履歴シートに `source='移行'` の行が1件でもあれば、止める（K-17）。
2. 移行用フォルダから4つの CSV を読む（`Utilities.parseCsv`）。どれかがなければ止める。
3. マスタ3つを書き込む（シートの2行目以降を置き換える）。
4. records.csv の各行を、入力チェック（§4）の規則で確かめる。ただし圧力の範囲・マスタとの関係・設定者の有効フラグは確かめない。設定者は記入称で入力者マスタを探し、見つからなければエラー（空はよい）。
5. changedAt の古い順（同じなら sourceRow の順）に並べ、採番する。
6. masterDiff を計算する。`source='移行'`、登録者と更新者は `SYSTEM`、登録日時と更新日時は今、version 1（K-18）。
7. まとめて書き込む（`setValues`）。時刻の列は先に書式を `@` にする。
8. ログ「移行データ取込」を書く。
- エラーが1件でもあれば、何も書き込まずに、エラーの一覧をダイアログに出す。

### 13.5 照合
取込のあと、ダイアログに次を表示する。Excel の値（2026/11/12 時点）と比べる。

| 項目 | 期待する値 |
|---|---|
| 件数 | 154件 |
| パターン別 | P1 8件、P2 64件、P3 30件、P5 52件 |
| 燃料別 | ガス 126件、重油 28件 |
| マスタとの差異 | 4件（移行元行 88、131、141、145） |
| 期間 | 2025/01/21〜2026/11/12 |
| 設定者が空 | 3件（移行元行 12、14、88） |

本番の取込のときは件数が増えているので、変換レポートの値と比べる。

## 15. マスタを変えたときの扱い

- パターンのメイン圧力を改定しても、過去の記録の圧力とマスタとの差異は変えない（D-15、K-09）。
- 入力者を無効にしても、過去の記録の表示（記入称）は変わらない。履歴の絞り込みでは選べる。
- 品種を無効にしても、過去の記録の品種はそのまま。新規の入力の選択肢には出さない。
- パターン・入力者ID・品種名の**値そのもの**を書き換えると、過去の記録とつながらなくなるので、書き換えずに新しい行を足す（docs/05 の運用に書く）。
